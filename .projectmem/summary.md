# projectmem - Project

_Last updated: 2026-10-28_

## Project purpose
Deploy PyTorch image-classification and YOLOv26 detection/instance-segmentation models to the AMD/Xilinx Kria KV260 using Vitis AI 3.5. The family-owned flow covers inspection, optional experimental pruning/fine-tuning, INT8 calibration/test, XMODEL compilation, manual deployment and board benchmarking. A two-class FaceHuman INT8 Fast Finetune artifact has a recorded 5,000-image KV260 experiment; broader model/task hardware validation remains pending.

## Decisions
- The platform deploys PyTorch classification and YOLOv26 detection/instance-segmentation models to Kria KV260 through Vitis AI 3.5: inspect -> optional family-owned pruning/fine-tuning -> INT8 calibration/test and XMODEL export -> compile -> manual transfer -> board benchmark. Hardware parity remains to be validated; pruning is experimental. [README.md]
- Current implementation is family-owned under kria_ai/: classification/ and yolov26/ prepare models, datasets, losses, preprocessing and postprocessing; common/ provides small task-independent Vitis/runtime/artifact/checkpoint APIs. The entry point is python -m kria_ai, dispatching classification or yolov26 detection/segmentation CLI commands. [kria_ai/cli.py]
- Registry implementation after the modular migration lives in frozen dataclasses at kria_ai/classification/config.py, kria_ai/yolov26/detection/config.py, kria_ai/yolov26/segmentation/config.py and kria_ai/common/board/config.py. Root model_config.py, dataset_config.py and board_config.py expose compatibility views; scripts/ entry points forward to kria_ai. Keep those public registry interfaces synchronized; do not duplicate model/board constants in stage scripts. [model_config.py]
- ArtifactPaths keys generated outputs by configured model ID under build/<model-id>/{inspector_report,optimizer_report,quantize_result,compiled}; XMODEL names are <model-id>_int.xmodel and <model-id>_kria.xmodel. Preserve baseline artifacts when experimenting by selecting a separate --build-root (for example build_fast_ft). Never hand-edit generated models, calibration data, datasets, weights or compiler artifacts. [kria_ai/common/artifacts.py]
- YOLOv26 host preparation/export is family-owned in yolov26/models.py, dpu.py and export.py; preserve DPU-friendly raw one2one outputs and CPU anchor-free decode/top-k without NMS. Detection uses yolov26/decode.py and detection/postprocess.py; segmentation additionally assembles masks in segmentation/masks.py. Keep class count, strides, reg_max, thresholds and output-layout contracts synchronized across config, calibration/test and board inference. [kria_ai/yolov26/export.py]
- KV260 hardware metadata and runner limits are centralized in common/board/config.py (DPUCZDX8G_ISA1_B4096, default 2 runners, allowed 1-4). Board runtime is shared but family benchmarks own preprocessing/postprocessing; XIR/VART imports must remain lazy and unavailable power/compute metrics must degrade gracefully off-board. Board transfer is currently manual, not automatic. [kria_ai/common/board/config.py]
- Detection and instance-segmentation own separate dataset/label parsers: detection requires 5-column normalized box rows; segmentation accepts polygon rows or COCO polygon JSON, not RLE-only masks. Calibration is image-only with deterministic subset indices. Host and board share yolov26/preprocess.py letterbox logic; preserve normalization, ordered classes, scale and padding consistently. [DATASET_PREPARATION.md]
- Detection profiling keeps shared StageProfiler and decode/accuracy algorithms unchanged. Existing aggregate dpu/postprocess/accuracy/write names remain; additive nested/sublevel and per-worker rows expose attribution. Start worker threads inside the application wall-time/power window so startup is consistently included, record runner_setup separately, and explicitly state no warmup exclusion. Preserve wall_pct as an uncapped accumulated-thread/wall ratio, never hardware utilization; detailed notes are stored in text and schema-v2 JSON. [kria_ai/yolov26/detection/benchmark.py]
- Present Kaggle FP32 as the user's unquantized corresponding-model baseline on the matched 5000-image test set, with GPU/FPGA stage comparisons in README/experiment guide. Use GPU batch1 versus Kria batch1 (1/1 and2/2 workers) as primary descriptive profiling comparison; retain batch16 and validator profiles separately. Broad stage roles are related but backend/head/evaluator/window differences remain explicit. Never sum overlapping stage times, infer missing GPU substages or claim isolated hardware/quantization effects. Keep source metrics frozen and deployment code unchanged. [README.md; docs/experiments.md; docs/evidence/]
- Present YOLO26n results as a four-configuration accuracy matrix (GPU FP32, pending GPU INT8, measured FPGA INT8 with user-confirmed 1,000-image Fast Finetune, pending FPGA INT8 without Fast Finetune), then the existing profiling comparison and bounded interpretation. Keep confidence-0.3 P/R/F1 separate in definition from confidence-0.001 AP; use GPU harmonic-of-macro-P/R F1 and explicit Pending/Not measured markers. Preserve fine-grained inventories in the experiment guide and no hardware/quantization isolation claims. [README.md; docs/experiments.md]
- Implement NumPy evaluation parity against downloaded Ultralytics 8.4.150 wheel SHA256 1af11709f0e525e72d8b1b71916c0081de3e63c49ab9ffdbffa995ae6a8c69de. Use validator IoU matching/AP for mAP and separate confusion-matrix matching for fixed-confidence P/R/F1 exactly as yolo-eval.ipynb; retain harmonic-of-macro-P/R F1 and explicit evaluator version metadata. Keep inference, historical metrics and dependencies unchanged; verify exact-source oracle and edge-case fixtures before claiming parity.
